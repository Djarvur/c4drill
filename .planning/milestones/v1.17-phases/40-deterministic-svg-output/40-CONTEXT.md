# Phase 40: Deterministic SVG Output - Context

**Gathered:** 2026-09-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Rendering the same model twice produces byte-identical output — generated `id="edge<N>"` SVG group ids derive deterministically from model content, never from Go map iteration order (issue #42). Fix ordering only; no change to rendered semantics, layout, or the id format itself.

</domain>

<decisions>
## Implementation Decisions

### Root-cause framing (scout-confirmed)
- **D-01:** The `edge<N>` ids are generated by GraphViz's own SVG emitter in edge **insertion order** — c4drill never writes edge ids itself (grep: no `id="edge` literals in Go source). Nondeterminism therefore enters through the ORDER edges are appended to the cgraph, not through id assignment. Prime suspect: `buildEdges` (internal/graph/builder.go:1030) walks `v.UnitOrder` (stable, definition order) for outgoing links, but incoming `LinksFrom`/`ResolvedLinksFrom` slices are synthesized by the validator (internal/validator/index.go mirrors every outgoing link into the target) — if that synthesis iterates a Go map, per-unit incoming order — and hence global edge insertion order — varies run to run.

### Ordering contract
- **D-02:** Determinism must be established at the SOURCE: incoming-link mirrors (`LinksFrom` / `ResolvedLinksFrom`) and any map-derived link collections must be ordered by a stable content key (source path, then authoring order) before edge construction — not fixed up after the fact at the SVG layer.
- **D-03:** DEFENSE-IN-DEPTH: `buildEdges` ends with a stable sort of the final edge slice by the edge's already-unique cgraph Name (`{source}_to_{target}_{n}`, assigned per-pair in walk order — builder.go:1097). With D-02 in place the sort is a no-op; if any future walk regresses, the sort still guarantees insertion-order stability. Per-pair sequence counters stay meaningful because pair walks are deterministic after D-02.
- **D-04:** Keep the SVG id format `edge<N>` exactly as GraphViz emits it today. Do NOT emit explicit edge ids into DOT — that would change DOT output and force wholesale golden re-baselining for zero user value.

### Verification contract
- **D-05:** TDD RED→GREEN: a regression test renders the issue #42 reproducer (10×10 generated `.c4d`) twice in-process and asserts byte-equal SVG output. RED on current code, GREEN after the fix. Byte-equality across repeated runs is likewise asserted for `dot` and `html` (REPRO-03).
- **D-06:** Golden policy: if any existing SVG golden shifts, the delta must be id-numbers-only (verify by canonicalizing ids before diff); re-baseline once. canonicalDOT goldens (DI-1/COMPAT-02/REF-05) are order-insensitive by design and MUST pass untouched — they are the no-semantic-change gate.

### Claude's Discretion
- Exact stable-sort key details (Name vs (Source,Target,seq)) and whether the fix lands in the validator mirror construction, `buildEdges`, or both — planner/researcher decide from the actual data flow.
- Test placement (builder vs render package) per existing test conventions.

</decisions>
