### Locked Decisions

### Root-cause framing (scout-confirmed)
- **D-01:** The `edge<N>` ids are generated by GraphViz's own SVG emitter in edge **insertion order** — c4drill never writes edge ids itself (grep: no `id="edge` literals in Go source). Nondeterminism therefore enters through the ORDER edges are appended to the cgraph, not through id assignment. Prime suspect: `buildEdges` (internal/graph/builder.go:1030) walks `v.UnitOrder` (stable, definition order) for outgoing links, but incoming `LinksFrom`/`ResolvedLinksFrom` slices are synthesized by the validator (internal/validator/index.go mirrors every outgoing link into the target) — if that synthesis iterates a Go map, per-unit incoming order — and hence global edge insertion order — varies run to run.

### Ordering contract
- **D-02:** Determinism must be established at the SOURCE: incoming-link mirrors (`LinksFrom` / `ResolvedLinksFrom`) and any map-derived link collections must be ordered by a stable content key (source path, then authoring order) before edge construction — not fixed up after the fact at the SVG layer.
- **D-03:** DEFENSE-IN-DEPTH: `buildEdges` ends with a stable sort of the final edge slice by the edge's already-unique cgraph Name (`{source}_to_{target}_{n}`, assigned per-pair in walk order — builder.go:1097). With D-02 in place the sort is a no-op; if any future walk regresses, the sort still guarantees insertion-order stability. Per-pair sequence counters stay meaningful because pair walks are deterministic after D-02.
- **D-04:** Keep the SVG id format `edge<N>` exactly as GraphViz emits it today. Do NOT emit explicit edge ids into DOT — that would change DOT output and force wholesale golden re-baselining for zero user value.

### Verification contract
- **D-05:** TDD RED→GREEN: a regression test renders the issue #42 reproducer (10×10 generated `.c4d`) twice in-process and asserts byte-equal SVG output. RED on current code, GREEN after the fix. Byte-equality across repeated runs is likewise asserted for `dot` and `html` (REPRO-03).
- **D-06:** Golden policy: if any existing SVG golden shifts, the delta must be id-numbers-only (verify by canonicalizing ids before diff); re-baseline once. canonicalDOT goldens (DI-1/COMPAT-02/REF-05) are order-insensitive by design and MUST pass untouched — they are the no-semantic-change gate.

## Summary

Issue #42 reports that rendering the same `.c4d` model twice produces SVG files that differ only in the generated `id="edge<N>"` group ids — the id *set* is identical, geometry is identical, and `-f dot` output is byte-identical. This research verified the exact mechanism in the codebase and confirms the CONTEXT.md root-cause framing (D-01) with one important refinement: the nondeterminism enters at `populateIncomingLinks` (internal/validator/index.go:53-85), which ranges over the `BuildIndex` **map** (`for sourcePath, sourceInfo := range index`) when appending mirror links into each target unit's `LinksFrom`. Go randomizes map iteration per run, so the per-target order of synthesized incoming mirrors — and therefore the global edge insertion order built by `buildEdges` — permutes between processes.

The downstream asymmetry the issue observed (dot stable, SVG permuted) is explained by how GraphViz consumes the cgraph: c4drill builds the same `graph.Graph` → `buildCgraph` → `gv.Render` path for every format (internal/render/render.go:96-131), but the XDOT writer emits edges grouped per node in out-edge order (per-source relative order is walk-stable even when global insertion order permutes), while the SVG emitter assigns sequential `edge<N>` ids by global insertion sequence. `html` inherits SVG output wholesale (RenderHTML funnels through `render(g, graphviz.SVG)`).

**Primary recommendation:** Fix at the source per D-02 — iterate the validator index in sorted key order when synthesizing `LinksFrom` mirrors (one sorted-keys loop in `populateIncomingLinks`) — then add the D-03 defense-in-depth stable sort of `g.Edges` by `Edge.Name` at the end of `buildEdges`. Pin with the D-05 TDD byte-equality regression test built from the issue #42 reproducer, run twice in-process through the full pipeline for `dot`, `svg`, and `html`.

### Pattern 1: Deterministic ordering at the source (definition/sorted order)
**What:** Anywhere a Go map feeds an ordered slice that reaches output, iterate sorted keys (or a pre-existing definition-order list like `v.UnitOrder` / `modelUnitOrder` / `subunitOrderOf`).
**When to use:** Every map→slice materialization in the parse→render pipeline.
**Example (the fix shape, verified against index.go:53-64):**
```go
// Source: internal/validator/index.go — populateIncomingLinks (this phase's fix)
sources := make([]string, 0, len(index))
for sourcePath := range index {
    sources = append(sources, sourcePath)
}
sort.Strings(sources)
for _, sourcePath := range sources {
    sourceInfo := index[sourcePath]
    // ... existing mirror-append body unchanged ...
}
```
Repo precedent for the walk-order pattern: `modelUnitOrder(m)` (scope.go:258) and `subunitOrderOf(unit)` (scope.go:295) — "definition order preserved by captureDefinitionOrder" is the project's canonical answer to map iteration (CONTEXT.md Established Patterns).

### Pattern 2: Defense-in-depth stable sort (D-03)
**What:** After slice construction, a stable sort by an already-unique content key makes the slice order a pure function of model content, even if a future walk regresses.
**Example:**
```go
// Source: internal/graph/builder.go buildEdges tail (this phase's fix)
slices.SortStableFunc(edges, func(a, b *Edge) int {
    return strings.Compare(a.Name, b.Name)
})
```
`Edge.Name` is unique per drawn edge (fix 260831-01u per-pair counters, builder.go:1094-1103), so the sort is a total order and a no-op once D-02 holds.

### Pattern 3: Byte-equality regression pin (D-05, issue-reproducer precedent)
**What:** Encode the bug report as a test: build the 10×10 model from the issue #42 Python generator, run the full pipeline twice in-process, assert `bytes.Equal` on each format's output.
**When to use:** Every byte-reproducibility bug. In-process repetition is sufficient — Go randomizes map iteration on every range statement, so two pipeline runs in one test process exercise different iteration orders (verified: `populateIncomingLinks` is called per `Validate` call, validator.go:22-25).
**Anti-patterns to avoid:**
- **Fixing at the SVG layer** (renumbering ids post-render): violates D-02/D-04; ids would no longer correspond to insertion order and goldens churn forever.
- **Sorting only `ResolvedLinksFrom`**: the direct `entry.Unit.LinksFrom` path (builder.go:1059) and `countIncomingPairs`/`collectPairAggregates` (builder.go:1156, 1310) read the same permuted slice — fix the synthesis, not the readers.
- **Subprocess-based reproducibility tests**: slow (process spawn × graphviz WASM) and unnecessary; in-process double-render catches map-order variance (this is also why the bug survived: no test ever rendered the same model twice).

## Common Pitfalls

### Pitfall 1: Map range in the mirror synthesis
**What goes wrong:** `for sourcePath, sourceInfo := range index` (index.go:54) yields a different source order every run; mirrors land in each target's `LinksFrom` in run-dependent order.
**Why it happens:** Go deliberately randomizes map iteration; the bug is invisible in single-render tests.
**How to avoid:** Sorted-key iteration (Pattern 1); add a validator-level unit test asserting `LinksFrom` mirror order is identical across N pipeline runs.
**Warning signs:** Any test that renders once and compares against a canonical (order-insensitive) form cannot catch this — only repeat-render byte equality can.

### Pitfall 2: Fixing the consumer instead of the producer
**What goes wrong:** Sorting inside `buildEdges`/`processIncomingLinks` alone leaves `resolveBoundaryNodeLinks` (scope.go:978-981) and `resolveSubunitCrossLinks` (scope.go:1080-1082, 1114-1116) copying permuted `LinksFrom` into `ResolvedLinksFrom`.
**Why it happens:** The permuted slice has many readers.
**How to avoid:** D-02 — order at synthesis time in the validator; keep D-03 as the builder-side net.

### Pitfall 3: Golden churn misread as semantic change
**What goes wrong:** After the fix, an SVG golden may shift because `edge<N>` numbers follow the (now stable, but possibly different-from-before) insertion order.
**Why it happens:** D-03's sort can reorder edges vs today's walk order.
**How to avoid:** D-06 policy — canonicalize `id="edge<N>"` before diffing; if the delta is id-numbers-only, re-baseline once; canonicalDOT goldens (DI-1/COMPAT-02/REF-05) must pass untouched since they are order-insensitive by design.

### Pitfall 4: dedup `seen` map dependence on walk order
**What goes wrong:** `markSeen(seen, edgeKey)` keeps the FIRST edge per pair (builder.go:1375, 1430); if incoming order changes, a different mirror becomes the surviving edge — potentially shifting collapsed-pair styling.
**Why it happens:** First-wins dedup is order-sensitive by design (D-01 first-wins, scope.go:1184-1186 comment).
**How to avoid:** After D-02, the first-seen mirror is deterministic (sorted source order) — surviving-edge choice is stable. Verify via the existing canonicalDOT goldens + the repeat-render byte test; do NOT change dedup semantics in this phase.
